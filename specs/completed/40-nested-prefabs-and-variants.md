# Spec 40: nested prefabs and prefab variants (authored from code)

Author, from a code builder, a prefab that INSTANCES another prefab inside itself (nested), and a
prefab whose base is another prefab and that carries an override layer (a variant), both round-tripped
and seamless. This is the depth layer on top of flat prefab authoring (`specs/completed/39-prefab-authoring.md`),
which shipped single-root prefab assets from one builder `.cs`. Nested authoring and variant authoring
ship TOGETHER in this one milestone. Everything binds to spec 39's shared build/sync target and to the
M10 / spec 24 override machinery; almost nothing here is new logic, it is composition.

## Measured foundation (spikes, with evidence)

The facts below were measured against the real editor or read out of the tree. None is derivable from
spec 39 or the foundation spec alone; each is the basis a decomposition builds on.

- **Nested authoring is tractable, and the nesting is genuine (not flattened).**
  `PrefabUtility.InstantiatePrefab(childAsset)` into the prefab-contents scene, parented under the
  root, then `SaveAsPrefabAsset` yields a real nested instance. On the reloaded asset the nested
  child reports `IsPartOfPrefabInstance == true`, `GetCorrespondingObjectFromSource` resolves to the
  child prefab, and the child's internal objects resolve to the child too. CONSTRAINT: the nested
  child MUST be a connected prefab instance at save time. Instantiate-then-parent; never build the
  child's objects inline, or the nesting flattens into loose GameObjects.
- **Nested identity is stable across edit-in-place regeneration.** When A is regenerated by editing
  its loaded contents (spec 39's edit-in-place path, `com.codescenes/Editor/PrefabBuildSyncTarget.cs:68`
  `LoadPrefabContents` -> mutate -> `:118` `SaveAsPrefabAsset`), A's own objects AND the nested child's
  internal objects keep their fileIDs. The spec-39 fileID-stability invariant holds at depth; it is the
  same mechanism, not a new one.
- **Variant create/save produces a real Variant.** `InstantiatePrefab(base)` (connected) -> mutate a
  field on the instance -> `PrefabUtility.RecordPrefabInstancePropertyModifications(instance)` ->
  `SaveAsPrefabAsset(instance, path)` produces an asset whose `GetPrefabAssetType == Variant` and whose
  root reports `IsPartOfVariantPrefab == true`. The override persists as a variant modification list
  (`GetPropertyModifications`), and a later base change inherits through to the variant. This is
  IDENTICAL for a code-defined base and a human-made base: measured, no API difference.
- **Depth >= 2 pair-uniqueness holds for asset-nested prefabs.** The `(targetObjectId, targetPrefabId)`
  pairs are unique within an instance and across independent instances at nesting depth >= 2, so v1
  does NOT cap nesting depth for identity reasons. (This is the asset-side confirmation of the
  depth-uniqueness gate spec 24 required for scene instances.)
- **The read side already detects a nested prefab.** `PrefabHierarchyReader.ResolveNestedPrefabGuid`
  (`com.codescenes/Editor/PrefabHierarchyReader.cs:124`) detects a nested prefab and stops descending,
  recording `NestedPrefabGuid` (`:115`); `GetCorrespondingObjectFromSourceAtPath` (`:141`) addresses a
  specific ancestor layer. The override machinery (`com.codescenes/Editor/PrefabInstanceProbe.cs` +
  `.Nested.cs` + `.Overrides.cs`, `SceneBuilder.Core/Identity/InstanceOverrideRecord.cs`,
  `SceneBuilder.Core/Identity/InstanceOverrideRehydrator.cs`,
  `SceneBuilder.Core/Diff/InstanceOverrideDiff.cs` `DetectStaleOverrides` at `:35`,
  `SceneBuilder.Core/Model/PrefabInstanceNode.cs`, `OverrideTarget.cs`, `PrefabInstanceKey.cs`) is
  provenance-agnostic. It already models a base ref plus `PropertyOverride[]` / added / removed
  collections, so base-vs-override disentanglement is INHERITED, not rebuilt.
- **Identity must be read from PERSISTED state.** An unsaved scene instance has an all-zero
  `GlobalObjectId`. Use the asset-side `GetGlobalObjectIdSlow` (stable immediately after save, the same
  off-scene stamp spec 39 uses at `com.codescenes/Editor/PrefabInstanceProbe.Nested.cs:75`) or read
  after save. `GetPrefabInstanceStatus` is scene-only; asset-side checks use `IsPartOfPrefabInstance`
  plus `GetCorrespondingObjectFromSource` / `...AtPath`. `GetCorrespondingObjectFromSource` returns only
  the immediate source layer; reaching a deeper layer needs `...AtPath`.

## The load-bearing constraint: one build/sync core, spec 39's target seam

Nested and variant build/sync route through spec 39's `IBuildSyncTarget`
(`com.codescenes/Editor/IBuildSyncTarget.cs:16`) and its prefab implementation
(`com.codescenes/Editor/PrefabBuildSyncTarget.cs`). There is no new target abstraction and no
`NestedPrefabTarget` / `VariantTarget` fork. The prefab target's four hooks (`ReadSnapshot`, `Execute`,
`MutationScope`, `Persist`) already carry the read/execute/persist shape both features need; this
milestone teaches the EXISTING prefab target to instance a child inside its contents and to save a
variant, it does not add a parallel writer.

Stated as owner plus mechanism, per the foundation invariant-hoisting rule:

- **ONE owner:** the prefab build/sync target. Every nested and variant write funnels through it.
- **ONE mechanism:** the spec-39 prefab target's `Execute` into `LoadPrefabContents(path).scene` plus
  `SaveAsPrefabAsset`, extended with the two save shapes measured above (instantiate-child-into-contents
  for nested; `RecordPrefabInstancePropertyModifications` before save for variant).
- **The check that fails on bypass:** the scope pass rejects a nested or variant code path that
  assembles or persists a prefab outside the prefab target. A duplicated writer is a defect, not a style
  choice.

## The child-must-be-connected invariant (measured; encoded as a checked mechanism)

**A nested child MUST be materialized as a CONNECTED prefab instance and parented into the contents. It
MUST NOT be built inline as loose objects.** Inline construction flattens the nesting: the reloaded
asset carries plain GameObjects instead of a nested instance, `IsPartOfPrefabInstance` reads false, and
`GetCorrespondingObjectFromSource` resolves to nothing. Stated as owner plus mechanism plus check:

- **ONE owner:** the prefab target's nested-materialize path.
- **ONE mechanism:** `PrefabUtility.InstantiatePrefab(childAsset, contents.scene)` (the same call
  `PlanExecutor` already runs for scene instancing at `com.codescenes/Editor/PlanExecutor.cs:149`),
  then reparent under the root, then `SaveAsPrefabAsset`.
- **The check that fails on bypass:** an EditMode test authors A instancing B, builds, reloads
  A.prefab, and asserts the nested child has `IsPartOfPrefabInstance == true` and
  `GetCorrespondingObjectFromSource` resolving to B. A materialize that built B inline fails it.

## The identity-from-persisted-state invariant (measured; encoded as a checked mechanism)

**Identity for a nested-instance object MUST be read from persisted state, never from an unsaved
in-contents instance.** A freshly instantiated, unsaved instance has an all-zero `GlobalObjectId`, so
stamping it before save records a useless id. Stated as owner plus mechanism plus check:

- **ONE owner:** the prefab target's identity-stamping step.
- **ONE mechanism:** stamp via the asset-side `GlobalObjectId.GetGlobalObjectIdSlow` over the loaded
  contents AFTER save (the spec-39 off-scene stamp; `idType=1`, `assetGUID` = the prefab GUID,
  `targetObjectId` = the object's local fileID), which Core stores as the opaque
  `IdentityMapEntry.GlobalObjectId` string.
- **The check that fails on bypass:** an EditMode test asserts a stamped nested-instance object's
  `GlobalObjectId` is non-zero and resolves back to the same object. A stamp taken before save records
  an all-zero id and fails it.

## Additions to the contract

Flagged here per foundation section 3. This milestone introduces NO new Core model value type and reuses
the M10 / spec 24 override collections verbatim.

- **Nested instance = a `PrefabInstanceNode` child of the prefab's `SceneModel`.** A prefab is a
  `SceneModel` with a single-element `Roots` (spec 39). A nested prefab is a `PrefabInstanceNode`
  (`SceneBuilder.Core/Model/PrefabInstanceNode.cs`) placed in that root's `Children`, which the model
  already allows because `PrefabInstanceNode` is a `GameObjectNode`. Its override collections
  (`Overrides` at `:16`, `AddedComponents` at `:19`, `RemovedComponents` at `:22`,
  `AddedGameObjects` at `:25`, `RemovedGameObjects` at `:28`, `ScopedOverrides` at `:34`) carry the
  overrides authored on the nested instance, keyed by `OverrideTarget` (`SubKey` / `ComponentType` /
  `ChildPath`) exactly as M10 and spec 24 key them.
- **Variant-ness = a variant marker plus a base `AssetRef` on the prefab's model and sidecar.** A
  code-authored variant records that this prefab asset IS a variant of base X: a variant flag and the
  base prefab's `AssetRef` (`SceneBuilder.Core/Model/AssetEntry.cs` shape, the self-registered prefab)
  persisted on the prefab's `SceneModel` and mirrored in the sidecar. The override layer the variant
  carries is the SAME `PropertyOverride[]` / added / removed collections above; a variant is a base ref
  plus an override list, which the existing model already expresses.

New authoring types (Unity-free, in `com.codescenes/Runtime/`):

- **`IPrefabVariantDefinition`**: the recognized shape for a variant builder, sibling to
  `IPrefabDefinition` (`com.codescenes/Runtime/IPrefabDefinition.cs`). It names a base
  (`PrefabRef Base { get; }`) and an override-only `void Build(VariantRoot root)`.
- **`VariantRoot`**: the override-only authoring root a variant configures, exposing the M10 / spec 24
  override verbs (`.Override(...)`, `.AddComponent<T>()`, `.RemoveComponent<T>()`, `.On(...)` at
  existing-vocabulary depth) against the inherited base, and no `.Add` of a fresh root (the root is the
  base).
- **A typed nested-instance verb on `NodeHandle`.** `NodeHandle.Instance(string)` already exists
  (`com.codescenes/Runtime/NodeHandle.cs:90`); a typed `Instance<TRef>(TRef prefab)` overload is added,
  paralleling `SceneRoot.Instance<TRef>` (`com.codescenes/Runtime/SceneRoot.cs:38`), so a child of a
  `PrefabRoot` builder nests a prefab by typed `Prefabs.X` ref and returns an `InstanceHandle<TRef>`
  carrying the M10 / spec 24 override verbs.

Sidecar: the spec-39 prefab sidecar gains the variant base ref (an `AssetEntry` for the base) on a
variant's map, and the nested instance registers its source-prefab GUID in `Assets[]` (merge-only,
never pruned). No new sidecar section.

Everything else binds to `00-foundation.md` verbatim (section 2 seam, section 3 model, section 4
identity, section 7 conflict, section 13 create-with-payload) and to spec 39 (the target seam, the
edit-in-place fileID invariant, prefab routing).

## Goal

From code: author a prefab A that instances prefab B inside its own hierarchy (nested), and author a
prefab variant whose base is another prefab and that carries an override layer (variant), each saved to
a `.prefab` on disk and kept in seamless bidirectional sync. An edit to A or the variant in Prefab Mode
reconciles back to the builder source; an edit to the builder source regenerates the asset edit-in-place,
preserving the nested child's and the variant's identities.

## In scope

- **Nested authoring (code -> prefab):** a `PrefabRoot` builder whose hierarchy contains a nested
  prefab instance (`node.Instance(Prefabs.B)`), materialized as a genuine connected instance inside the
  loaded contents and saved, per the child-must-be-connected invariant.
- **Variant authoring (code -> prefab):** an `IPrefabVariantDefinition` naming a base and an
  override-only `Build`, materialized via `InstantiatePrefab(base)` ->
  `RecordPrefabInstancePropertyModifications` -> `SaveAsPrefabAsset`, producing a real Variant asset.
  The base may be ANY prefab, human-made OR code-defined; measured, there is no API difference.
- **Overrides at existing-vocabulary depth** on a nested instance and on a variant: an override reaches
  what today's selector / handle vocabulary addresses (the base's or the nested instance's own
  hierarchy, its root and direct children), authored with the M10 / spec 24 verbs.
- **Round-tripped and seamless:** a nested-instance edit or a variant-field edit made in Prefab Mode
  reconciles back to the builder `.cs`; a builder edit regenerates the asset edit-in-place. Both
  directions run through spec 39's prefab target and under the persisted master auto toggle
  (`com.codescenes/Editor/SceneBuilderAutoToggle.cs`), no buttons on the happy path.
- **Edit-in-place stability at depth:** regenerating A keeps its own objects' AND the nested child's
  internal objects' fileIDs stable (the spec-39 invariant, proven at depth).
- **A variant overriding a field the base authored is allowed and silent.** That is what a variant is;
  M10's override targeting already keeps the override on the variant, not the base.

## Out of scope

- **Deep, layer-qualified override addressing.** v1 override depth is existing-vocabulary only: an
  override reaches the base's or the nested instance's own root and direct children (what today's
  selector / handle vocabulary addresses). Addressing an object several nested layers down (a
  layer-qualified deep reference into a nested prefab's nested prefab) is DEFERRED to a follow-up.
- **Deep multi-layer references** into or across nested prefabs beyond the existing-vocabulary depth
  above.
- **Anything spec 39 already ships:** flat single-root prefab authoring, the target seam extraction,
  the edit-in-place fileID mechanism, prefab routing, and `Assets[]` self-registration. This milestone
  builds ON them, it does not re-specify them.
- **Multi-root prefabs.** A prefab is single-root (spec 39); a variant's root is the base's root.

## Authoring API

Nested authoring reuses the `PrefabRoot` builder and adds a typed nested-instance verb on a child node.
A nested prefab instance carries the M10 / spec 24 override verbs at existing-vocabulary depth:

```csharp
public class Turret : IPrefabDefinition
{
    public void Build(PrefabRoot root)
    {
        var turret = root.Add("Turret");
        turret.Component<TurretController>(c => c.Set(x => x.range, 12f));

        // nested: a connected instance of the Gun prefab, parented under the turret root
        turret.Instance(Prefabs.Gun)
              .Override(g => g.Set((GunController c) => c.fireRate, 6f))   // existing-vocab depth
              .AddComponent<AudioSource>();
    }
}
```

Variant authoring is a dedicated `IPrefabVariantDefinition`: a base plus an override-only `Build`:

```csharp
public class SportsCar : IPrefabVariantDefinition
{
    public PrefabRef Base => Prefabs.Car;                     // base may be code-defined OR human-made

    public void Build(VariantRoot root)
    {
        root.Override(c => c.Set((CarStats s) => s.topSpeed, 260f));   // overrides only
        root.AddComponent<SpoilerWing>();
        root.On(sel => sel.FrontLeftWheel, w => w.Override(x => x.Set((Wheel c) => c.grip, 1.4f)));
    }
}
```

- `node.Instance(Prefabs.B)` (the new typed `NodeHandle.Instance<TRef>` overload, sibling to
  `SceneRoot.Instance<TRef>`, `com.codescenes/Runtime/SceneRoot.cs:38`) nests a connected instance of B
  under `node` and returns an `InstanceHandle<TRef>` exposing the M10 / spec 24 override verbs.
- `IPrefabVariantDefinition.Base` names the base by typed `PrefabRef`; `VariantRoot` exposes ONLY the
  override verbs (no `.Add` of a fresh root, since the root is the base). Overriding a field the base
  authored is allowed and silent.
- **The parser needs two recognition arms**, both sibling to the spec-39 arm. `BuilderParser.FindBuildMethod`
  (`SceneBuilder.Core/Parsing/BuilderParser.cs:123`) already accepts `ISceneDefinition` and
  `IPrefabDefinition` (`:131`); a `VariantRoot`-parameter arm is added for `IPrefabVariantDefinition`,
  and a nested-`Instance` call inside a `PrefabRoot` body is recognized the same way `SceneRoot.Instance`
  is. Recognition is the only parse change; the override statement grammar is reused from M10 / spec 24.

## Core deliverables

Mostly reuse, stated explicitly:

- **No new Core model value type.** A nested prefab is a `PrefabInstanceNode` child (above); a variant
  is a base `AssetRef` plus the existing override collections. `Diff`, `Materialize`, `Reconcile`,
  source-patch, canonical serializer, and `IdentityMap` are reused.
- **Represent variant-ness:** a variant marker plus base `AssetRef` on the prefab's `SceneModel` and
  sidecar, and the recognition that a `VariantRoot` builder's statements lower to override collections
  against the inherited base rather than a fresh root.
- **Represent a nested-instance-as-prefab-child:** a `PrefabInstanceNode` in a prefab root's `Children`,
  including the case where the outer container is an ASSET (not a scene). The override read/diff/reconcile
  is provenance-agnostic (measured), so the M10 / spec 24 code applies unchanged.
- **The diff producing the variant override list and the nested instance.** `Diff` over a prefab
  `SceneModel` that contains a nested `PrefabInstanceNode` emits the instantiate plus the override plan
  ops the M10 / spec 24 path already emits; `Diff` over a variant `SceneModel` emits the base
  instantiate plus the variant's override list. No new Plan op is introduced (the override ops and
  `InstantiatePrefab` already exist).
- **Parser recognition arms** for `IPrefabVariantDefinition` / `VariantRoot` and for a nested `Instance`
  call inside a `PrefabRoot` body.

## Editor adapter deliverables

All built by the pipeline, EditMode-gated, all inside spec 39's prefab target.

- **Nested materialize** (the child-must-be-connected invariant's mechanism): inside the prefab target's
  `Execute` into the loaded contents, instantiate the child with
  `PrefabUtility.InstantiatePrefab(childAsset, contents.scene)`, reparent under the root, and let
  spec 39's `SaveAsPrefabAsset` persist it. Never build the child inline. The override plan ops on the
  nested instance execute through the existing `InstanceOverrideExecutor`
  (`com.codescenes/Editor/InstanceOverrideExecutor.cs` + `.Children.cs`).
- **Variant materialize:** inside the prefab target, `InstantiatePrefab(base)` (connected) -> apply the
  variant's overrides on the instance -> `PrefabUtility.RecordPrefabInstancePropertyModifications(instance)`
  -> `SaveAsPrefabAsset(instance, path)`, yielding `GetPrefabAssetType == Variant`. Identical mechanism
  for a code-defined and a human-made base.
- **Identity stamping for nested-instance objects** (the identity-from-persisted-state invariant's
  mechanism): asset-side `GlobalObjectId.GetGlobalObjectIdSlow` over the loaded contents AFTER save
  (`com.codescenes/Editor/PrefabInstanceProbe.Nested.cs:75`), stored as Core's opaque string. Never
  stamp an unsaved in-contents instance.
- **The reconcile that reads a nested instance's or a variant's overrides back** and patches the builder
  `.cs`, reusing M10 / spec 24: `PrefabInstanceProbe` (`.cs` / `.Nested.cs` / `.Overrides.cs`) reads the
  override layer, `PrefabHierarchyReader.ResolveNestedPrefabGuid`
  (`com.codescenes/Editor/PrefabHierarchyReader.cs:124`) detects the nested boundary, and
  `ReconcilerInstances` (`SceneBuilder.Core/Reconcile/ReconcilerInstances.cs`) emits the source patch.
  For a variant, the override list is read via `GetPropertyModifications` and lowered through the same
  path. Base changes inherit through Unity and are NOT reconciled onto the variant.
- **Routing and triggers unchanged from spec 39.** Nested and variant builders live under `Prefabs/`
  (`SceneBuilderPaths.PrefabBuildersFolderName`, `com.codescenes/Editor/SceneBuilderPaths.cs:50`); the
  `Prefabs/*.cs` `FileSystemWatcher` (`com.codescenes/Editor/SceneBuilderAutoSync.cs:213`) drives
  code -> prefab, and the Prefab-Mode `ObjectChangeEvents.changesPublished` subscription
  (`com.codescenes/Editor/SceneBuilderAutoSync.cs:136`) drives prefab -> code, both under
  `SceneBuilderAutoToggle.Enabled`.

## Composition / identity / sidecar

- **A nested instance keys on the M10 pair-key model.** An object inside a nested prefab has the outer
  asset's identity and the nested instance's `PrefabInstanceKey` (`SubKey` = `(TargetPrefabId,
  TargetObjectId)`); overrides on it key on `OverrideTarget(SubKey, ComponentType)`
  (`SceneBuilder.Core/Model/OverrideTarget.cs`), which the sidecar persists as
  `InstanceOverrideRecord` (`SceneBuilder.Core/Identity/InstanceOverrideRecord.cs`) and re-derives the
  `ChildPath` from. Provenance-agnostic: the container being an asset rather than a scene does not
  change the keying (measured).
- **A variant records its base.** The variant's sidecar carries the base prefab's `AssetEntry` (GUID),
  and the variant's own overrides persist as `InstanceOverrideRecord[]` against the base's objects. A
  variant overriding a base-authored field stays on the variant, not the base (M10 override targeting).
- **Depth >= 2 needs no depth cap for identity** (measured pair-uniqueness); the
  `GetCorrespondingObjectFromSourceAtPath` correspondence chain remains the authoritative fallback
  spec 24 mandated, reused here for the asset-side case.
- **Prefab-internal renames and reparents** reconcile through the existing structural-matching identity
  model (foundation section 4), unchanged.

## Decomposition guidance

The seam-reuse invariant and the two measured invariants (child-must-be-connected, identity-from-persisted-state)
are this milestone's cross-cutting invariants. Hoist each per the foundation invariant-hoisting rule:
name the owner, the shared mechanism, and the check that fails on bypass. Do NOT restate any of them as
per-task guidance across the tasks. Reuse spec 39's target seam as the ONE build/sync core; a nested or
variant path that forks a new target or a second writer is the defect the seam-reuse invariant exists to
catch.

Two buckets, ordered nested-first (nested is the make-or-break save shape; the variant save reuses its
identity-stamping and reconcile plumbing).

### Bucket A: nested prefab authoring

1. **A1 Authoring surface + parser recognition (Core + Authoring).** Add the typed
   `NodeHandle.Instance<TRef>` overload (`com.codescenes/Runtime/NodeHandle.cs`, sibling to
   `SceneRoot.Instance<TRef>` at `com.codescenes/Runtime/SceneRoot.cs:38`); recognize a nested `Instance`

   `SceneBuilder.Core.Tests/`, `unity-gate/Assets/GateTests/`.

   (`PrefabUtility.InstantiatePrefab(childAsset, contents.scene)`), reparent under the root, save via the
   existing `SaveAsPrefabAsset`, and stamp nested-instance identity asset-side AFTER save. Own both

   `com.codescenes/Editor/PrefabHierarchyReader.cs:124`), patch the builder `.cs`

   `Prefabs/` triggers under the master toggle.
   TOUCHES: `com.codescenes/Editor/PrefabInstanceProbe.cs` / `.Nested.cs` / `.Overrides.cs` (declare if

Rules that bind the decomposition:

- **Owned-defect files in TOUCHES, or split.** Every file a task edits belongs in its TOUCHES. A task
  that would touch a file it did not declare must be split.
- **Pin the whole symmetric operation set, not a subset.** The nested/variant reconcile matrix
  (add / remove / field-change / rename / reparent on the nested instance and the variant override list)
  is pinned as a whole in A3 and B2; pruning it to a subset is the failure the rule prevents.
- **Reuse the seam; do not fork.** A3 and B2 route through the spec-39 prefab target. A new target or a
  second prefab writer is caught by the scope pass.

All EditMode (the adapter boundary), one assertion each:

1. Author a nested prefab from code (A instances B), build. Expected: A.prefab contains a genuine
   connected B instance (`IsPartOfPrefabInstance == true`, `GetCorrespondingObjectFromSource` -> B), not
   flattened GameObjects.
2. Edit B's field on the nested instance in code at existing-vocabulary depth, let auto-sync fire.
   Expected: the nested instance's override is reflected on the reloaded asset.
3. Edit the nested instance in Prefab Mode, let auto-sync fire. Expected: the builder `.cs` gains the
   override, no button pressed.
4. Regenerate A edit-in-place after a structural change. Expected: an unchanged object in A and an
   unchanged object inside the nested B instance both keep their fileIDs.
5. Author a variant of a code-defined base, build. Expected: a real Variant asset, the override
   persists, and a base change inherits through.
6. Author a variant of a human-made base, build. Expected: identical result to step 5 (no API
   difference).
7. Edit a variant field in the editor, let auto-sync fire. Expected: the variant `.cs` gains the
   override; a base-authored field the variant did not touch is not reconciled onto the variant.
8. Scene regression: build and sync a scene builder. Expected: scene behavior is unchanged through the
   shared seam.

## Risks / notes

- **Connected-at-save or it flattens.** The single make-or-break behavior: a nested materialize that
  builds the child inline instead of `InstantiatePrefab`-then-parent-connected produces loose
  GameObjects, not a nested instance. The connected-nesting EditMode test is the guard.
- **Identity from persisted state.** An unsaved in-contents instance has an all-zero `GlobalObjectId`;
  stamp asset-side after save. `GetPrefabInstanceStatus` is scene-only; asset-side checks use
  `IsPartOfPrefabInstance` plus `GetCorrespondingObjectFromSource` / `...AtPath`.
- **`GetCorrespondingObjectFromSource` returns only the immediate source layer.** Reaching a deeper
  nested layer needs `GetCorrespondingObjectFromSourceAtPath`; this bounds v1 override depth to the
  existing-vocabulary depth (root and direct children), with deep layer-qualified addressing deferred.
- **v1 override-depth boundary is a stated line, not an accident.** An override at existing-vocabulary
  depth is in scope; a layer-qualified deep reference several nested layers down is out of scope this
  pass and belongs to the follow-up. State the boundary in the authoring surface so a deeper address
  fails loud, never silently mis-targets.
- **Do not fork the target.** Nested and variant build/sync route through spec 39's prefab target; a
  second writer is the defect the seam-reuse invariant exists to catch.
