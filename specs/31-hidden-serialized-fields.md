# Spec 31 — The component reader enumerates serialized state, not inspector-visible state

> **Why this spec exists.** Live-editor testing (2026-07-30) found `Canvas.m_SortingOrder` never
> syncing scene→code: authored as `c.Set("m_SortingOrder", 3)`, set in the editor to 7, 9, 21 and 41,
> the builder source stayed at `3` and every sync answered "Scene already matches code — nothing to
> sync". Code→scene worked. In the same sync cycle `CanvasScaler.m_ReferencePixelsPerUnit` and
> `Rigidbody.m_Mass` patched normally, so neither transport nor node identity was involved.
> The reader was walking the component with `SerializedProperty.NextVisible`.

## The rule

`SerializedObject.GetIterator()` + `NextVisible` yields exactly the properties a **default inspector
would draw**. That is a rendering concept, not a data concept. Round-tripping is a data concern, so
`SerializedFieldBridge.CollectFields` (and `ReadNested`, one level down) walks with **`Next`** and
filters by explicit name.

Measured in 6000.5.3f1 across 18 built-in component types, `NextVisible` drops four groups:

| Group | Examples | Disposition |
|---|---|---|
| Object/prefab serialization bookkeeping | `m_ObjectHideFlags`, `m_CorrespondingSourceObject`, `m_PrefabInstance`, `m_PrefabAsset`, `m_GameObject` | never surfaced (`Bookkeeping`) |
| MonoBehaviour editor bookkeeping | `m_EditorHideFlags`, `m_EditorClassIdentifier`, `m_Name` | never surfaced (`Bookkeeping`) |
| Authored state a **custom editor** draws by hand, plus state drawn outside the property list | `Canvas.m_SortingOrder` / `m_SortingLayerID` / `m_TargetDisplay`, `Rigidbody.m_Constraints`, `Renderer.m_SortingOrder` / `m_SortingLayerID` / `m_SortingLayer`, `m_Enabled` (component header) | **captured** — this is the bug class |
| Renderer state regenerated by a lightmap bake / static batching / editor selection | `m_LightmapIndex(Dynamic)`, `m_LightmapTilingOffset(Dynamic)`, `m_StaticBatchInfo`, `m_StaticBatchRoot`, `m_SelectedEditorRenderState` | never surfaced (`DerivedBuildState`) — build output, not authored data; writing it into the builder source would push stale bake results back onto the scene on the next rebuild |

Not part of the rule: foldout expansion. Measured — `NextVisible(enterChildren: true)` enters children
regardless of `isExpanded` in 6000.5.3f1.

One carve-out, `ClosedGrammarComponents`: `SceneBuilder.Authoring.FitSize` and
`SceneBuilder.Authoring.SurfaceSnap` are authored through a dedicated closed-keyword call
(`.FitSize(height: 2f)`, `.SurfaceSnap(down: true)`) whose argument set is fixed, so `m_Enabled` is
not surfaced for them — the writer would emit `.FitSize(m_Enabled: false)` and the parser would then
reject its own output. Disabling a `FitSize` releases its channel; that is what syncs, through the
transform.

The exclusion lists are matched by **property path at the top level only**, and both the live read and
the per-type default template are built by the same `CollectFields` call, so pruning and template
cannot diverge.

## Unity confirmation checklist

Covered by `unity-gate/Assets/GateTests/HiddenSerializedFieldSyncTests.cs`:

- `Canvas.sortingOrder` edited in the scene is captured by `ReadComponent`.
- `Rigidbody.m_Constraints` (hidden, custom-drawn) is captured — the fix is the class, not one field.
- A disabled component surfaces `m_Enabled`.
- Serialization/editor bookkeeping stays out of a managed component's fields.
- Renderer bake/batching state stays out.
- A disabled `FitSize` does **not** surface `m_Enabled`.
- End to end through the real sync: an authored `m_SortingOrder` edited 3 → 7 reaches the builder
  source, and a second sync reports no change (the field settles).
- End to end: a never-authored `m_SortingOrder` is introduced into the source without losing the
  field already authored on that component.
